Subfeature-Local Slice Migration Plan

Proposal to align execution slices with the subfeatures they implement, while reducing duplicate slice-contract paperwork by folding most brief.md content into blueprint.md and removing the separate requirements checklist for new slices.

Discussion Draft Scope: sirius-skills workflow Decision: mandatory for new subfeatures Decision: remove new checklists Date: 2026-07-12

Executive Summary

The current workflow treats subfeatures as the default delivery unit, but execution slices still live in a central root-level slices/ tree or, after the existing migration helper, in a feature-level slices/ tree. That creates an ownership mismatch: the detailed implementation plan is physically separated from the subfeature planning packet that owns the work.

Decision: all new subfeature work must create execution slices under the owning subfeature. Existing root or feature-level slices should be migrated there when traceability can identify a single subfeature owner.

At the same time, make blueprint.md the primary per-slice execution artifact by adding a short slice-contract section at the top. Keep brief.md only as an optional clarification artifact or a minimal compatibility stub, and stop creating checklists/requirements.md for new slices.

Current State

Subfeature planning Lives under docs/features/<feature>/subfeatures/<subfeature>/ and owns subfeature intent, impact analysis, design, planned slices, and traceability.
Execution slices Currently live under the configured slice_dir, usually root slices/.
Existing migration target migrate-slices currently targets feature-local docs/features/<feature>/slices/, not subfeature-local slices.
Brief and blueprint split brief.md captures the contract; checklists/requirements.md validates that contract; blueprint.md captures implementation details. For small slices, this duplicates planning and validation content.

Proposed Target Layout

docs/features/<feature>/
  subfeatures/<subfeature>/
    discover.md
    impact-analysis.md
    system-design.md
    slice-planning.md
    slice-traceability.md
    .subfeature-meta.json
    .skills/
      execution.json
    slices/
      README.md
      registry.json
      <slice-id>-<slice-slug>/
        blueprint.md
        brief.md              # optional or compatibility stub
        .slice-meta.json
        checklists/           # legacy only; not created for new slices

This keeps the planning backlog, planned-to-execution traceability, execution plan, and execution lifecycle metadata inside the same durable delivery scope.

Ownership Model

Artifact Owner Purpose
.subfeature-meta.json Subfeature lifecycle Records child capability status, approval, affected artifacts, and ready slice IDs.
slice-planning.md breakdown Defines planned slices, increments, dependency order, and validation hints.
slice-traceability.md breakdown and execution bootstrap Maps parent story IDs to planned slice IDs and execution slice IDs or paths.
slices/registry.json guide-execution tooling Tracks execution-slice lifecycle state inside the subfeature scope.
blueprint.md blueprint Primary execution artifact: slice contract, technical plan, traceability, validation, and detailed design.
brief.md brief, optional Only needed when the slice contract needs clarification before technical planning, or retained as a legacy stub.
checklists/requirements.md Legacy validation artifact Do not create for new slices. Preserve and read for legacy slices only; move useful checks into blueprint.md validation gates.
.slice-meta.json Execution slice lifecycle Records execution-slice status, path, timestamps, and relation metadata.

Brief Minimization

The concept of a slice contract is still useful. The redundant part is requiring a standalone full brief.md for every slice when blueprint.md already needs to map requirements to implementation and validation.

Compatibility stub

For tools that still expect brief.md, generate a minimal file instead of duplicating the full contract:

# Slice Contract

Canonical execution plan: `blueprint.md`

This slice contract is captured in the "Slice Contract" section of `blueprint.md`.

Long-form brief.md remains valid when intent is ambiguous and the team wants an explicit contract review before implementation planning.

Readiness decision: brief_ready becomes a legacy state. New normal slice flow should move from draft to blueprint_ready or execution_ready once blueprint.md contains the slice contract and implementation plan.

Checklist decision: stop creating checklists/requirements.md for new slices. Legacy checklists remain readable, but validation should move into blueprint.md through requirement traceability and validation gates.

Migration Plan

  1. Codify the rule. Document that all new subfeature work must create execution slices under the owning subfeature, while root and feature-level slice roots are compatibility locations only.
  2. Update execution scope resolution. Teach slice, ship, ship-slice, guide-execution, review-execution, and close-slice to prefer the selected subfeature path as the execution scope.
  3. Create subfeature execution config. When bootstrapping from a subfeature, create <subfeature>/.skills/execution.json with slice_dir: "slices" if missing.
  4. Enhance migrate-slices. Use subfeature slice-traceability.md files to map existing execution slice IDs to a single owning subfeature.
  5. Move matched slices. Move root or feature-level execution slice folders into <subfeature>/slices/, preserving active and archived slices.
  6. Rewrite registries. Remove migrated rows from old registries and add them to the subfeature-local slices/registry.json with paths relative to the subfeature scope.
  7. Preserve traceability. Ensure slice-traceability.md still maps each planned slice to the migrated execution slice ID and, if useful, the relative execution slice path.
  8. Minimize brief.md. Update blueprint templates and validators so a blueprint-owned slice contract satisfies normal execution readiness.
  9. Remove new requirements checklists. Stop generating checklists/requirements.md for new slices and move its useful validation checks into the blueprint.md template and readiness validation.
  10. Keep compatibility reads. Reporting, tracing, audit, repair, archive, and close flows should continue reading root and feature-level slice roots during the migration period.
  11. Deprecate root slices. After migration, mark root slices/ as legacy and avoid using it for new subfeature delivery work.

Phased Rollout

Phase Change Expected Outcome
1 Docs and templates Workflow guidance says subfeature-local execution slices are mandatory for new subfeature work, blueprint.md owns the default slice contract, and new slices do not create checklists/requirements.md.
2 Validation compatibility Execution validation accepts either legacy brief.md plus blueprint.md, or blueprint.md with a valid slice-contract section. brief_ready and checklists/requirements.md are treated as legacy.
3 New-slice bootstrap New slices created from subfeature planning land in <subfeature>/slices/.
4 Migration dry run migrate-slices --dry-run reports target subfeatures, blocked ambiguities, and planned registry rewrites.
5 Migration execution Matched slices move into subfeature-local slice roots without losing archived history or lifecycle metadata.
6 Legacy cleanup Root slices/ remains readable for compatibility but is no longer a preferred write target.

Validation Criteria

  • New subfeature slices are always created under the owning subfeature.
  • ship <subfeature> can resume or bootstrap work without relying on root slices/.
  • trace-artifacts, report-artifacts, audit-artifacts, repair-artifacts, and archive-artifacts can find subfeature-local execution slices.
  • close-slice still invokes owner-completion reconciliation for the linked subfeature.
  • blueprint.md contains the complete contract plus implementation plan for normal slices.
  • brief.md is optional or minimal and no longer duplicates the same contract in full.
  • checklists/requirements.md is not created for new slices; equivalent checks are enforced through blueprint.md.

Risks and Mitigations

Risk Mitigation
Ambiguous ownership: a legacy slice maps to multiple subfeatures or none. Block migration for that slice and emit a report entry requiring manual traceability repair.
Tooling misses nested registries: reporting or close flows only read root slices/. Update inventory discovery before moving slices, and keep root reads as compatibility fallback.
Brief or checklist removal breaks validators. Support legacy brief.md and checklists/requirements.md during transition, but make blueprint.md sufficient for new-slice readiness.
Migration rewrites too much state. Require dry-run reports, preserve archived slices, and avoid destructive cleanup in the migration command.

Open Decisions

  1. Resolved: subfeature-local slices are mandatory for all new subfeature work immediately. Compatibility support remains only for legacy root slices, legacy feature-level slices, direct feature work during transition, and migration-only feature-level slice roots.
  2. Resolved: brief_ready becomes a legacy state used only for existing slices or explicit standalone-brief flows.
  3. Resolved: remove checklists/requirements.md for new slices. Preserve legacy files, but move required checks into blueprint.md.
  4. Resolved: feature-level docs/features/<feature>/slices/ roots are migration-only once subfeatures are universal.
